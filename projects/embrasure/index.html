Why this assay

If any entry of sandbox.filesystem.denyRead or sandbox.filesystem.denyWrite is not a string — object {"path": "~/.ssh"}, or a number — Claude Code 2.1.261 accepts the settings file, exits zero, prints no warning and writes nothing to stderr, and then applies neither permissions.deny nor any PreToolUse hook for that run.

The failure is open, not closed. A Read of a path covered by a permissions.deny rule succeeds. The PreToolUse hook — the documented escape hatch — is never invoked. The hook writes a witness file before it decides; if witness.txt does not exist after the run, the hook was never invoked.

Deleting the sandbox key entirely restores enforcement. So adding a sandbox deny list that looks more restrictive makes the file strictly less restrictive. An unknown key inside sandbox is harmless. additionalDirectories string/object/number/null cells were all harmless. Object and number behave identically. Decisive pair: 4/4 string enforced, 4/4 object unenforced.

Expected: a sandbox block the CLI does not accept should at worst be ignored, leaving enforcement no weaker than if the block were absent. Fail loudly on a non-string entry. Do not let a sandbox problem disable deny rules and PreToolUse.

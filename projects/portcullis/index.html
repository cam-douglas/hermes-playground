Research brief

        

          Primary:
          anthropics/claude-code#92278
          (OPEN, bug, has repro, platform:macos, area:core, regression, filed ~2026-09-05).
          Since Claude Code 2.1.259 (seen in 2.1.261), EACCES when traversing
          /Library/Managed Preferences on macOS is treated as an unreadable
          managed policy instead of an absent one. That arms
          policy_unreadable_fail_close, prints fatal startup warnings naming
          a leaf plist that may not exist, and blocks auth.
        

        

          Unable to read managed policy settings... Contact your administrator.
        

        

          Jamf left /Library/Managed Preferences at mode 000
          (d--------- root:wheel); default would be drwxr-xr-x.
          No Claude Code policy plist exists at the device-level or per-user path — the
          org pushes no Claude Code policy. Older 2.1.257 / 2.1.258 used
          existsSync, which returned false on EACCES (empty
          plistStdouts, no fail-close).
        

        

          Cousin cite-only:
          #91816
          (WSL /mnt/c inaccessible, same EACCES-as-unreadable-policy
          regression class). Cite only. Primary stays #92278.
        

      


      

        
1 — Untraversable courtyard, not a locked vault

        

          /Library/Managed Preferences is mode 000
          (d--------- root:wheel). Neither
          /Library/Managed Preferences/com.anthropic.claudecode.plist
          nor the per-user path exists. The org pushes no Claude Code policy.
        

        
2 — accessSync forgives only ENOENT / ENOTDIR

        

          Since 2.1.259 / 2.1.261, accessSync(path, R_OK) turns
          EACCES into a fatal unreadReason record. That
          record arms the auth gate policy_unreadable_fail_close.
        

        
3 — existsSync treated EACCES as absent

        

          2.1.257 and 2.1.258 used existsSync, which returned false
          on EACCES → empty plistStdouts, no fail-close.
        

        
4 — The warning names the wrong stone

        

          Startup shows two fatal managed-settings warnings (per-user + device-level)
          with EACCES on the leaf plist paths. The ancestor directory
          that actually failed is not named.

Research brief

On Windows, a clean network interface change — undocking a laptop, so the USB-dock Ethernet NIC goes away and Wi-Fi takes over — kills the in-flight streaming request and ends the turn with no retry. The session prints API Error: Connection lost mid-response. The response above may be incomplete. and stops. There is no Retrying (n/10), and no system/api_error record is written to the session JSONL.

This is not a broken-network report. The interface swap is orderly and the new path is healthy within ~2 seconds; every other program on the machine rides through it. The client simply never tries again. All six published occurrences were sessionKind: bg. Interactive users can press enter. Background jobs silently idle — one for 16 hours, another with queued task-notifications 25 minutes later that still produced no turn. Five hits inside the Windows event-log window land on the same second as NetworkProfile id=10001 Disconnected.

Hypothesis (issue text, NON-BINDING): a mid-stream socket loss should be retried like any other transient network error — re-resolve, open a fresh TCP connection on the current default route, and resume the turn. At minimum a background session should not silently go idle.

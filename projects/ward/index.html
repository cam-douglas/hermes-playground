1 — Same directory, different ward

        

          Docs say CLAUDE_CONFIG_DIR keys the Keychain entry to
          that directory. When the directory is byte-identical to
          $HOME/<demo-home>/.claude, only whether the env
          var is textually present differs — and login is fully lost.
        

        
2 — Trailing slash and sibling still miss

        

          CLAUDE_CONFIG_DIR="$HOME/.claude/" and
          CLAUDE_SECURESTORAGE_CONFIG_DIR="$HOME/.claude" still
          read loggedIn false. The slash and the sibling hash do
          not rejoin the unset slot.
        

        
3 — Empty-pin workaround nulls identity

        

          CLAUDE_CONFIG_DIR="$HOME/.claude" CLAUDE_SECURESTORAGE_CONFIG_DIR=""
          restores loggedIn true but nulls email and orgId. A
          returned login with no identity is not a matched keyway.
        

        
4 — No diagnosis; automations reproduce it

        

          claude auth status and “Not logged in · Please run
          /login” never name the store. Automations that unconditionally
          forward CLAUDE_CONFIG_DIR to children reproduce the
          mis-ward even when the parent never had the var set. Keychain-only
          OAuth — no .credentials.json.
        

        
Expected (from the issue)

        

          An explicit default path should consult the same Keychain entry as
          leaving the variable unset. Auth status should print which store
          was tried. Forwarding the default path should not drop login.
        

        
Likely path (NON-BINDING)

        

          Keychain account/service string incorporates the literal presence
          of CLAUDE_CONFIG_DIR (or routes through a
          SECURESTORAGE hash) even when the resolved path equals
          the default; the diagnosis path never prints the selected store id.
          Discard if evidence disagrees. Do not claim unseen source.

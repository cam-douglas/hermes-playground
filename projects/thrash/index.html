Why this assay

Claude Code 2.1.237 blocks the main thread ~40–60s on the first prompt of every new process. The TUI looks dead. This reproduces with --safe-mode, no user MCP, Haiku, and a one-file git repo.

Debug: silence between Sending 12 skills via attachment (initial) and first byte after 40832ms. [event-loop-stall] blocked for 40808ms … cpu=40899ms rss=2646MB heap=896MB. CPU time ≈ wall time, so this is synchronous main-thread work, not I/O. The detector's [likely sleep/wake] tag is misleading.

Isolation ruled out user MCP, opus[1m], large workspace, session history, and user config. Every new process pays again. Same pattern without --safe-mode: 50–64s, RSS up to ~3.5 GB.

Hypothesis only (NON-BINDING): something between skills-attachment send and first API byte does heavy synchronous main-thread work (possibly skill/attachment materialization or related), ballooning RSS and stalling the event loop; detector mis-tags sleep/wake. Verify nothing — encode issue facts only. Do not invent runtime source claims.

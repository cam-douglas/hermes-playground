Why this assay

On macOS 26.6.2 with VS Code 1.135.0 and the Claude Code VS Code extension, Edit/Write replace files via temp-file + rename rather than modifying in place. The path is unchanged but the inode is new, so any watcher bound to the original inode never fires.

Measured: inode BEFORE 5588409 → AFTER 5588677. Same path, different file object. The editor keeps showing stale A and believes the buffer is clean. The user types A′. files.autoSave: "afterDelay" writes A′ about a second later. B is lost. No conflict dialog.

Workspace recursive directory watchers observe the rename, so in-workspace files usually reload. Files opened outside any workspace folder — e.g. ~/.claude/plans/ — are watched individually and reproduce every time.

Expected: write in place (same inode), or copy content back into the original inode after rename, or emit an explicit change signal. Related but distinct: #87056 frames the same symptom as a race and asks for collision detection. #92419 is narrower: the editor is never notified.

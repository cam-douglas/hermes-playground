Research brief

CLAUDE.md / auto-memory sits in messages[0] after the system breakpoint, with no cache_control of its own. Docs and the "Prompt caching is everything" post describe project context as its own cached layer, shared by parallel sessions in the same directory. In practice the block is the first content block of the first user message, the user's prompt is a later block of that same message, and the next cache_control marker is on a session-context message that contains a per-session UUID. No request ever writes a cache entry ending at the project bed, so no other session can read it.

Primary: anthropics/claude-code#94417 (OPEN). Labels: bug, has repro, area:core. Claude Code 2.1.270 (also 2.1.266); Windows 11; Opus 5; subscription (1h TTL); both CLI and desktop. 703 session starts; 474 warm. Zero cross-session hits beyond the system prompt layer. CLAUDE.md+MEMORY is roughly 4–7k tokens that would be byte-identical between sessions of the same directory. Hypothesis (issue text, NON-BINDING): project context is placed inside messages[0] after the system breakpoint without its own cache_control, so no cacheable prefix ends at that layer and parallel sessions never share it.

Desired (narrative only): put a cache_control marker on the CLAUDE.md block (messages[0].content[0]), or move the block to system[4] with its own marker, ahead of the first user prompt. Session context stays per-session.

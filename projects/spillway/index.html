Research brief

        

          Primary OPEN issue:
          anthropics/claude-code#92311.
          Title: CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS is skipped when ultracode is active — a Workflow ran 7 agents under a cap of 3 (2.1.261).
          Labels: bug, has repro, platform:linux, area:agents.
        

        

          Cousin cite-only:
          #80082
          (closed docs — omitted the concurrent cap entirely)
          and
          #90483
          (open enhancement — Workflow concurrency derives from CPU count, too low on 2-vCPU cloud). Different symptom. Cite only.
        

        

          Backups (document only, not built):
          #92286 Cresset,
          #92292 Symlink,
          #92269 Louver.
        

      


      

        
1 — Launch guard early-return

        

          In Claude Code 2.1.261 the subagent launch guard returns early when
          appState.ultracode === true (and effort resolves to xhigh),
          so CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS never gates the
          Workflow tool that ultracode uses. A second, unrelated early return is
          gated by feature flag tengu_amber_kestrel.
        

        
2 — Measured seven-wide under a cap of 3

        

          Settings cap=3, ultracode on. Workflow agentCount:16 planned.
          Sweep-line over agent-*.jsonl timestamps peaked at 7 concurrent
          at 2026-09-05T08:21:20.624Z. FAIL transcript-gate lines for 4, 5, 6, 7.
        

        
3 — Runtime bound is CPU, not the env var

        

          Workflow runtime concurrency is min(16, availableParallelism()−2)
          — 16 on a 48-CPU host — and that, not the env var, bounded the run.
        

        
4 — Docs omit the impact

        

          Docs say ultracode sessions are exempt in one sentence. The impact —
          the cap does not apply to the fan-out mode — is not stated.
        

        
5 — Workaround that works (measured)

        

          A SubagentStart hook that counts live agents and exits 2 when the count
          would exceed the cap. Measured: 28 Agent dispatches under a hook cap of 2
          → never more than 2 running, 11 refused before spawn.
        

        
Expected (from the issue — checklist, not implemented here)

        

          With the cap at 3, no more than 3 subagents run at once for any executor,
          or the documentation states plainly that ultracode is the exception and
          how to cap it.
        

        
Likely path (NON-BINDING)

        

          The desk should make “ultracode early-return skips
          CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS so Workflow fans out past the
          operator’s cap” visceral via a dam board where the spillway opens.
          Discard if evidence disagrees. Do not claim unseen source.

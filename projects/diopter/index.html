Why this assay

Claude Code 2.1.260, macOS 26.5, M5 Max. Two consecutive claude -p "hi" runs in the same directory, captured via ANTHROPIC_BASE_URL. Measured against a local model so usage.input_tokens is readable and the cache is controlled.

The system prompt embeds the scratchpad directory path, which contains a per-session UUID. That UUID is the only thing that differs between two otherwise byte-identical requests — and because it sits inside the cached prefix, everything after it is invalidated on every new session.

Diff: tools 223,596 chars (137 MCP tools) byte-identical, same order; messages 50,534 chars byte-identical; system 7,483 chars differs at exactly one place. Path /private/tmp/claude-501/<project>/<SESSION-UUID>/scratchpad. Example UUIDs fc9aab5b-da05-4cc7-bbe2-410a1c472151 vs 88966ec9-2cb4-4872-bc6b-624b66257462. Same UUID also in metadata.user_id (not part of the prompt; harmless).

Cold 104.3 s / 65,303; identical prompt again 0.3 s / 5; next session only-UUID-differs 30.6 s / 16,157; same request with UUID normalised 0.4 s / 5. End-to-end with MCP: 131.7 s → 17.3 s → 8.3 s after the normalisation insight.

Suggested rails from the issue (cheapest first — not claimed implemented): move the scratchpad path out of the cached prefix (last user turn / late system-reminder); make the path derivable and stable per project; place the volatile segment as late as possible so tools (223 KB) stay in the shared prefix.

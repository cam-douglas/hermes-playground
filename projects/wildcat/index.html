Why this assay

On Claude Code 2.1.2xx (observed 2026-08-20; still the same on 2.1.260), macOS arm64, zsh, with permissions.defaultMode: auto, a Bash call issued with run_in_background: true whose command spawns detached children via nohup <cmd> > log 2>&1 & is reported completed as soon as the parent shell exits.

A follow-up ps aux | grep <cmd> right after the notification sometimes showed no matching processes. The model concluded the launch failed and relaunched the same workers. Later ps showed two processes for the same --worker-id. Both generations wrote the same output file concurrently, producing ~1.8× duplicate rows.

Two separable issues. Completion semantics: "completed" means the shell exited, not that the work finished. Process visibility: immediate ps can miss processes that appear ~5s later.

Minimal repro: run_in_background true with nohup sh -c 'for i in $(seq 1 60); do echo tick $i >> /tmp/bg_probe.log; sleep 1; done' > /dev/null 2>&1 & → completion within ~1s exit 0; immediate ps sometimes empty; wait ~5s and ps lists the process; the log keeps growing for 60s after completed.

Expected: report live descendants at exit, or document shell-exit-only and that detaching children inside run_in_background is unsupported; document any teardown visibility window. Workaround: never nest nohup … &; re-check ps after a few seconds.

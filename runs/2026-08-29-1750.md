## Problem

A new login is not a hold. On macOS, Claude Code stores OAuth in Keychain items named `Claude Code-credentials` plus hash-suffixed copies. A grant often writes a *new* item instead of updating the live one. CLI and desktop compute different hashes from advertised scopes / client identity, so they never share. Stale items are never GC'd. A second store (`~/.claude/.credentials.json`) can diverge: Keychain-only rotation vs file-only `/login` splits the refresh-token family and forces re-auth. A TUI success string can print while nothing persisted.

## Why Fob

A fob is the numbered tag hanging on a hotel key rack. Score the board. Name the class or admit **hung**. Idle word is **hung** (one live service, stores agree, no stale litter, CLI and desktop share). When a grant writes a new hash-suffixed item: **minted**. When items accrete without GC: **hoard**. When Keychain mdat and file mtime diverge: **split**. When `/login` reports success but nothing persisted: **false-cut**. When CLI vs desktop scope sets diverge: **scope-key**.

Verdicts: hung, minted, hoard, split, false-cut, scope-key.

The desk scores one new fact: KEYCHAIN CREDENTIAL LITTER. Did the login reuse the live fob, or mint another? A login success string is not a hold.

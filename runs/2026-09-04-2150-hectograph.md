Facts from the issue only:

- Claude Code 2.1.259, also seen on 2.1.252 and 2.1.258. macOS darwin 25.6.0 arm64. OTLP gRPC to otelcol-contrib 0.160.0 on loopback.
- The binary references five content flags: `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_RAW_API_BODIES`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_USER_PROMPTS`. None of them suppresses full bash command text.
- Measured with a canary string in a bash command, captured at a local collector with no processors, so the payload is exactly what Claude Code emits.
- Configuration table: all flags unset (default) → canary yes; `OTEL_LOG_TOOL_CONTENT=0` → canary yes; `OTEL_LOG_TOOL_CONTENT=false` → canary yes.
- It lands in three attributes, and only in tool attributes, never in the assistant response body:
  - `tool_decision` → `tool_parameters`, which contains `full_command`
  - `tool_result` → `tool_parameters`
  - `tool_result` → `tool_input`, which contains `command`
- `user.email` arrives as a record attribute on the same events.
- What should happen: one of the `OTEL_LOG_TOOL_*` flags should gate `tool_input` and `tool_parameters`. Failing that, the monitoring docs should say plainly that tool arguments and `user.email` are always exported and cannot be disabled.
- Anyone pointing Claude Code straight at a vendor OTLP endpoint, which the docs present as supported, is exporting every developer's shell commands and email address without meaning to.

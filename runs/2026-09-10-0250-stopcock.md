Facts from the issue body only:

- A Streamable HTTP MCP `tools/call` that must stay open for several minutes (human-in-the-loop wait) still errors with `is_error: true` and content `"The operation timed out."`
- Consistently narrow ~352–363 second window (measured 352.x, 363.1, 362.5, 357.8 — an 11-second spread)
- Every documented timeout knob was applied at once: per-server `timeout` 86400000 (24h); `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0` (confirmed received as 0); server `http.Server.requestTimeout=0` ruled out — timing unchanged
- MCP server stays healthy and reachable; the Claude client aborts its own `tools/call`
- Minimal repro: bare Streamable HTTP MCP whose one tool deliberately never responds (`wait_forever`)
- Claude Code 2.1.266; Ubuntu/Debian Linux; transport `type:http` Streamable HTTP, not SSE
- CLI emits `tool_progress` heartbeat events at `elapsed_time_seconds` 300 and 330 shortly before the timeout fires — call is not treated as silent/idle, yet still aborts
- Expected: honor the 24h ceiling, or (per the `=0` docs, "disables the check entirely") not idle-timeout at all, for as long as the server stays connected

Hypothesis only (NON-BINDING): the Claude client may apply a fixed undocumented internal wall-clock ceiling around ~360s to Streamable HTTP MCP `tools/call` that ignores the documented per-server timeout and `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT=0`. Invite verify against #93143 text only.

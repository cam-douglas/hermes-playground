Facts from the issue only:

- Claude Code CLI **2.1.261**; node **v22.17.0**; Linux (WSL2); model `claude-haiku-4-5-20251001`. `--settings` file with `--setting-sources ''` against a target carrying no settings of its own. `permissionMode`: `acceptEdits`. Every file carried `"allow": []`.
- If any entry of `sandbox.filesystem.denyRead` or `denyWrite` is not a string (object `{"path":"~/.ssh"}` or a number), the CLI accepts the settings, exits 0, prints no warning, writes nothing to stderr, and then applies **neither** `permissions.deny` **nor** any PreToolUse hook.
- Fail-open: a `Read` of a path covered by `permissions.deny` succeeds; the PreToolUse witness hook never fires (`witness.txt` never written).
- Deleting the `sandbox` key entirely restores enforcement. Adding a sandbox deny list that looks more restrictive makes the file strictly less restrictive.
- Decisive pair: string vs object, all else equal — 4/4 enforced with the string form, 4/4 entirely unenforced with the object form.
- Eight sandbox spellings × three commands (24 cells): key absent / string with enabled / string without enabled / unknown key all enforce; object denyRead (with or without enabled) / object denyWrite / number `[42]` all fail-open.
- `additionalDirectories` string/object/number/null over two commands: all harmless. Effect is specific to denyRead and denyWrite.
- Not Bash-only: object denyRead lets a denied `Read` succeed (contents returned). Write happened to stop only because `-p` has nobody to grant approval.
- Expected: a block the CLI does not accept should at worst be ignored, leaving enforcement no weaker than the key-absent row. Fail loudly on a non-string entry. Do not let a sandbox problem disable deny and PreToolUse.

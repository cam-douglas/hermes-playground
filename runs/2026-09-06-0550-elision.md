Facts from the issue only:

- Claude Code behavior read in v2.1.246; observed live on v2.1.246, v2.1.258 and v2.1.259. OS: Windows 11 Pro.
- Partial compaction **"Summarize up to here"** keeps everything after the anchor **except** prior compact summaries. Any earlier summary (e.g. from a previous "Summarize from here") that sits after the anchor is silently removed from the live context — it is neither summarized (outside the summarized range) nor preserved (filtered out of the kept suffix).
- When rebuilding the preserved suffix, the client filters out compact boundaries **and** prior compact-summary messages (`type === "user" && isCompactSummary`). Excluding stale boundary markers is fine; applying the same filter to summary messages deletes irreplaceable content.
- Entries remain in the session `.jsonl` but live context loses them permanently. A summary is the only in-context representative of hundreds of already-compacted messages.
- Case A (v2.1.246, Aug 31): one "up to here" cut dropped **four** earlier "from here" summaries (04:14, 05:07, 06:52, 08:10); `preservedMessages` had 153 entries — none a summary; re-attached file refs survived while summaries did not.
- Case B (v2.1.259, Sep 4): chain of four partials; two "up to here" cuts discarded **three** of four summaries.
- Case C (v2.1.259, Sep 4): "from here" preserved an initial summary before its anchor (UUID in preserved list); next "up to here" anchored before a "from here" summary did not — UUID missing from rebuild list even though position fell inside preserved range; session later reported only one summary.
- Reproduced: create "Summarize from here" near end → then "Summarize up to here" on a message older than that summary's anchor → prior summary S is gone.
- Workaround: never anchor "up to here" before an existing summary; prefer `/compact` or "Summarize from here".
- Expected: prior compact summaries after the anchor should be preserved like any other post-anchor content, or at least warn that N earlier summaries will be discarded.

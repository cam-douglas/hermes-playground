Title: Fullscreen renderer auto-disables itself on machines running many concurrent sessions (false boot-canary strikes). Labels: bug / has repro / platform:macos / area:tui. Env: Claude Code 2.1.251 native install; macOS 15.x Darwin 25.6.0 arm64. Canary landed in 2.1.236. Filed by evertjr.

Facts from the issue only:

- User runs 10–20 Claude Code sessions concurrently, burst-launched and torn down together. settings.json has `"tui": "fullscreen"`. Fullscreen itself works; it renders every time.
- Messages: "Claude Code's fullscreen renderer didn't finish starting last time on this machine, so this launch is using the classic renderer…" then "…has repeatedly failed to start on this machine, so it has been turned off here."
- `fullscreenAutoDisabled` in `~/.claude.json`: `{"version": "2.1.251", "at": 1788146545484, "strikes": 4}`. Sticky threshold is 2; landing on 4 means several strikes were banked from a single scan (orphaned `fullscreenBootPending`), not four failed launches.
- Pending map is keyed by PID in the single shared `~/.claude.json`. Every concurrent session adds an entry at startup and removes it ~10s later. Burst start+settle = read-modify-write races; lost updates leave entries for dead PIDs. Next launch reads those as crashed boots.
- Strikes only clear on a healthy settle. Signal-driven exit settles as withdrawn: removes that PID's entry but preserves the strike counter. Machines that terminate rather than quit interactively only ratchet up.
- PID reuse is a false positive: an entry whose PID matches the launching process's own PID is counted as a strike immediately, without checking it is the same process (no `startedAt` vs process start).
- Repro: set tui fullscreen; launch ~15 sessions concurrently each in its own pty; let them pass the 10s healthy mark; terminate the group; relaunch; watch `fullscreenBootStrikes` / `fullscreenAutoDisabled`.
- Widening SIGTERM-to-SIGKILL grace made it worse (more writers at once) — contention, not truncation.
- Workaround: `CLAUDE_CODE_NO_FLICKER=1` → entry path `env_on`, excluded from the set that arms the canary, so nothing is written and nothing can be orphaned; fullscreen stays on.

## Problem

FALSE BOOT-CANARY. Shared PID-keyed pending map + lost updates + strike banking from one burst snuffs a working fullscreen renderer. The gauze lamp is the canary; the flame is the renderer.

## Why Davy

A Davy lamp is a miner's safety lamp whose brass gauze is supposed to warn when firedamp is present — without snuffing a working flame. The boot-canary is that lamp: it is supposed to warn when the fullscreen renderer failed to start. On a machine running many concurrent sessions, lost updates on a PID-keyed pending map in shared `~/.claude.json` bank false strikes from a single burst, then the working flame is snuffed and the classic renderer is forced. A false canary is not a hold. Score the gauze. Name the class or admit **lit**. Idle word is **lit**. When working fullscreen is auto-disabled by a false boot-canary: **snuffed**. When `fullscreenAutoDisabled.strikes` are banked (4 vs threshold 2): **struck**. When leftover `fullscreenBootPending` entries remain for PIDs that are gone: **orphaned**. When `pid === ownPid` is counted as a strike without `startedAt`: **reused**. When a signal-driven exit settles withdrawn and preserves the strike counter: **withdrawn**. When machines that terminate rather than quit only ratchet the counter up: **ratcheted**. When 10–20 concurrent sessions launch together: **burst**. When concurrent RMW hits one `~/.claude.json`: **lost-update**. When the classic renderer is forced despite fullscreen working: **classic**. When the pending map is keyed by PID in the single shared file: **pid-keyed**. When `CLAUDE_CODE_NO_FLICKER=1` excludes the canary: **env-on**.

Verdicts: lit, snuffed, struck, orphaned, reused, withdrawn, ratcheted, burst, lost-update, classic, pid-keyed, env-on.

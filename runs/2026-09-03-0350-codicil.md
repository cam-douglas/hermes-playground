Title: In a shared multi-agent working tree, `git commit --amend` doesn't re-check HEAD, so it can silently rewrite a concurrent teammate's commit instead of the agent's own. Labels: bug / has repro / area:agents. Reporter KinohTaGo.

Facts from the issue only:

- Agent Teams session; multiple teammate agents sharing one non-worktree-isolated git working tree.
- Agent A creates commit C1, then intends to `git commit --amend` solely to append a required tag to the commit message.
- Before A's follow-up amend, Agent B commits C2 on top of C1 (parent = C1), making C2 the new HEAD.
- A's `git commit --amend` does not re-check HEAD. `--amend` operates on whatever the current HEAD is, not on "the commit I personally just made."
- It rewrites Agent B's C2: keeps C2's file tree byte-identical (no data lost) but discards B's commit message and replaces it with A's.
- Expected: before amend in a possibly-shared tree, verify `git rev-parse HEAD` still equals the SHA from the agent's own prior commit; refuse or warn if HEAD moved.
- Impact: git history/metadata only (message + parent linkage); no working-tree file loss.
- Version: Claude Code 2.1.239. Deterministic given the described interleaving.
